# Розробка та релізи Kopanka

Основний маршрут: `feature/* → dev → main`.

- `dev` — інтеграція задач, початкова гілка нової роботи та ціль звичайних PR.
- `main` — релізна гілка. PR сюди дозволений тільки з `dev` цього репозиторію.
- Довгоживучі `dev` і `main` не видаляємо та не переписуємо через force push.
- GitHub default branch — `dev`. Для production у Railway явно вказуємо `main`.

## Нова задача

```sh
git switch dev
git pull --ff-only origin dev
git switch -c feature/short-task-name
# Внести зміни та виконати перевірки.
git add <files>
git commit -m 'feat: describe the change'
git push -u origin feature/short-task-name
```

Відкрити PR **у dev**, дочекатися CI та злити. Підтримуються префікси
`feature/`, `fix/`, `hotfix/`, `chore/`, `docs/`, `refactor/`, `test/`, `ci/`,
`perf/`, `build/`, `dependabot/`. Squash зручний для задач; merge commit теж дозволений.
Назва префікса не визначає деплой. Навіть hotfix проходить через `dev`.
Не переносити в реліз випадкові незавершені задачі: у `dev` вливаємо готові зміни.

## CI та захист

Workflow запускається на PR у `dev`/`main`, push у ці гілки та вручну.
Обов'язкові checks:

- `branch-policy`: перевіряє маршрут PR, включно з локальним походженням `dev` для релізу.
- `verify`: чисте встановлення залежностей, Prisma generate, міграції з нуля,
  typecheck всіх пакетів, unit/API тести, повний сценарій із реальною тимчасовою
  PostgreSQL-базою, production-збірки player web і admin web.

CI не використовує production-секрети. Telegram/S3 вимкнені в інтеграційному
сценарії; база ізольована в runner. Усі jobs повинні завершитися успішно перед
merge; гілка має бути актуальна відносно цільової. Розмови review треба закрити.
Другий reviewer не обов'язковий, щоб не блокувати розробника, який працює сам.
Захист поширюється і на адміністраторів; force push і видалення вимкнені.
Не вимикати захист для обходу невдалого CI — виправити причину через PR.

## Реліз

1. Перевірити готовність задач у `dev`, зміни міграцій/env і основний сценарій на телефоні.
2. Відкрити PR `dev → main`, описати склад релізу та перевірки.
3. Дочекатися `branch-policy` і `verify`.
4. Злити через **Create a merge commit**. Не використовувати squash/rebase для
   цього PR: довгоживучі гілки мають зберігати спільну історію.
5. Railway, налаштований на `main`, підхоплює зміни. Перевірити
   стан деплою API/web/admin, health API і сценарій входу/запису. Зелений CI
   не підтверджує успішний деплой чи роботу reverse proxy.
6. Відкрити PR `main → dev` і злити merge commit для синхронізації історії.
   Це єдиний дозволений службовий PR із `main` у `dev`. Якщо після релізу
   гілки ще відрізняються лише merge-комітом, синхронізацію варто зробити
   до створення наступних задач; при вимозі up-to-date вона буде потрібна
   перед наступним релізом.

`dev` не означає автоматично окремий staging. Для нього потрібні окремі
сервіси Railway та БД, з branch `dev`, власними URL, CORS і build variables.
Не підключати тестове середовище до production-БД або каналу Telegram.
Поточні налаштування Railway цим workflow не змінюються й потребують окремої перевірки.

## Якщо PR відстає

У task-гілку можна злити свіжу `origin/dev`, вирішити конфлікти й виконати push;
CI перезапуститься. Для `dev`/`main` використовувати лише PR. Після релізу
для синхронізації створювати PR `main → dev`, а не робити прямий push у `dev`.
